# 项目自述：施工规范审查 Agent

> 这份文档是给你自己看的面试弹药库。每一节都是一个真实发生过的技术故事：
> 问题是什么 → 为什么会这样 → 我怎么解决的 → 结果如何。
> 面试前把这四个故事讲熟，做到不看稿能讲 2 分钟/个。

## 一句话介绍（电梯陈述）

我做了一个面向土木工程的规范审查 Agent：把各种格式的规范（文字版 PDF、扫描版 PDF、Word）
解析入库，按条文级别切分和检索，用户描述施工方案后，Agent 自主调用检索和校核工具，
生成带条文出处的审查报告，可导出正式 Word 文档。全套基于本地大模型（Ollama + Qwen2.5 7B），
数据不出本机，Docker 容器化部署。自建 25 题评测集，检索命中率 100%。

## 故事一：为什么按条文切分，而不是固定长度切分

**问题**：第一版用 LangChain 的 RecursiveCharacterTextSplitter 每 500 字切一段。
测试发现规范条文经常被从中间切断——比如某条 800 字的条文被切成两块，
提问时向量检索只召回后半块，前半块里的适用条件（"当采用500MPa及以上钢筋时…"）丢了，
模型基于残缺上下文给出错误结论。

**分析**：通用切分器只看字符不理解结构。但规范文本天然有结构：章（"6 承载能力极限状态计算"）、
条（6.3.1）。条文是规范的最小语义完整单元，应该按条文边界切分。

**方案**：写了正则识别行首条文号（`\d{1,2}(\.\d{1,3}){1,3}`），按条文边界切块，
每块附元数据：规范名、编号、条文号、章节、页码。超长条文再用递归切分兜底，但保留同一条文号。
表格用 pdfplumber 单独提取转 Markdown 入库。

**真实数据的坑**（这段最能打动面试官）：拿真实规范 PDF 测试后发现文字层质量极差——
条文号 `3.0.2` 被提取成 `3. O. 2`（数字0变字母O），`2.0.10` 变成 `2. o. l()`。
我加了一层编号清洗（O→0、l→1、()→0、去空格，清洗后校验必须是合法编号格式才替换）；
目录页的"……页码"行会产生假条文号，加规则过滤；章标题被排版拆成两行（"3"和"基本规定"各一行），
加了跨行拼接。修复后条文识别从一片混乱变成完整连续序列（1.0.1→1.0.2→…→3.0.10）。

**结果**：回答能精确标注出处——"《建筑工程施工质量验收统一标准》GB 50300-2013 第 3.0.2 条 (第11页)"。
对规范审查场景，能不能引用条文号是玩具和产品的分界线。

**可能的追问**：
- Q: 条文号正则误匹配怎么办（正文里出现"图4.3.7-1"）？
  A: 只匹配行首 + 清洗后校验合法格式；仍有少量误判（如表格里的数字），但评测显示不影响检索质量，
     进一步可以按条文号序列连续性做校验。
- Q: 为什么不用大模型来切分？
  A: 成本和确定性。80 页规范让 LLM 逐段判断太慢太贵，正则+规则是确定性的、免费的、可调试的。
     工程上"能用规则解决的不要用模型"。

## 故事二：评测驱动的 embedding 选型（50% → 100%）

**问题**：切分修好后，条文号直查很准，但自然语言提问经常召回错误内容。
比如问"未实行监理的建筑工程由谁履行监理职责"，正确答案在 3.0.2 条，但向量检索召回的是无关条文。

**方法**：不猜，先量化。自建评测集（问题 + 期望关键词 + 期望条文号），写自动评分脚本，
只测检索层（检索是 RAG 质量瓶颈，且可自动判分；生成层不好自动评）。
基线：nomic-embed-text 的关键词命中率 50%、条文命中率 50%。

**分析**：nomic-embed-text 主要面向英文训练，中文语义区分度弱。

**方案**：换 bge-m3（BAAI 出的多语言 embedding，中文效果公认好），
写了 rebuild_embeddings.py——直接从旧 FAISS 索引取出文档块重新向量化，
不用重新解析 PDF 和跑 OCR（省 6 分钟）。

**结果**：同一评测集，关键词/条文命中率都从 50% 提到 100%（后扩充到 25 题仍保持 100%）。

**过程中的工程坑**：420 块文档一次性提交给 Ollama embedding 接口，Ollama 运行时直接崩溃。
改成 64 块一批分批提交，420 块 9 秒完成。（教训：对外部服务永远要考虑批量上限。）

**可能的追问**：
- Q: 25 题 100% 是不是评测集太简单/过拟合？
  A: 承认局限——题目是我出的，且部分题在换模型前就见过。更严谨做法是盲测集 + 更大题量 +
     引入 MRR/NDCG 等排序指标。但方法论是对的：先建评测，再做优化，用数字说话。
- Q: 为什么不用 rerank？
  A: 下一步计划。当前召回已够用；如果库扩到几十本规范，会加 bge-reranker 做二阶段精排。

## 故事三：为什么 Agent 必须调工具（一次真实的幻觉事故）

**问题**：Agent 第一版测试时，输入"C25 混凝土用于预应力混凝土构件，请审查"。
模型**没有调用任何工具**，直接凭记忆回答，并且**编造了条文**：
说"GB 50010-2015 第 6.4.3 条规定预应力混凝土不应低于 C40"——
规范年份错了（是2010）、条文号是编的、数值也不对（正确答案是第 4.1.2 条、C30）。
答案看起来极其专业，全是错的。这种错误在工程领域是会出安全事故的。

**分析**：7B 小模型的参数记忆不可靠，而且它"不知道自己不知道"。
解决思路不是换更大的模型（治标），而是**让数值和条文永远来自工具，模型只负责决策和组织语言**（治本）。

**方案**：
1. 用 LangGraph 的 ReAct Agent 挂三个工具：search_spec（检索知识库）、
   check_concrete_strength（混凝土强度校核，数据表硬编码自 GB 50010-2010 表4.1.4）、
   check_steel_strength（钢筋强度查询）。
2. 系统提示词强约束："你自己的记忆不可靠，禁止凭记忆回答任何数值或条文，
   第一步必须先调用工具"。没有这句时 qwen2.5:7b 经常跳过工具；加上后稳定调用。
3. 界面展示工具调用轨迹，让用户看到每个结论的依据链。

**结果**：同一问题，Agent 调用 check_concrete_strength 拿到"最低要求 C30（第4.1.2条），
C25 不满足"，报告结论正确且出处真实。

**这个故事的价值**：它回答了"为什么要 Agent 而不是直接问大模型"——
不是为了赶时髦，是因为**工具调用是治幻觉的架构手段**。确定性的事（查表、算数、检索）交给代码，
模型只做它擅长的（理解意图、组织语言）。

**可能的追问**：
- Q: 7B 模型工具调用的稳定性？
  A: 靠三点兜底：强约束提示词、temperature=0、recursion_limit 防死循环。
     生产环境我会换 14B+ 或云端 API，并加"工具未调用时拒绝输出结论"的硬校验。

## 故事四：部署——从"我电脑上能跑"到"别人能用"

**现状**：Docker 容器化。应用打成镜像，模型不进镜像——容器通过
`OLLAMA_BASE_URL=http://host.docker.internal:11434` 连宿主机的 Ollama，
向量库用 volume 挂载持久化。docker compose up -d 一条命令启动。

**为什么这么设计**（分离部署的三个理由）：
1. 镜像瘦：模型 6GB 塞进镜像，构建和分发都是灾难；
2. 独立扩缩：模型服务和应用的资源需求完全不同（GPU vs CPU），分开才能各自扩容；
3. 可替换：换模型只改环境变量，不用重建镜像。

**如果真的要多人用（面试标准答案）**：
Gradio 换 FastAPI 拆成接口 + 前端独立；Ollama 换 vLLM（支持并发批推理）；
FAISS 换 Milvus/pgvector（并发读写、权限）；加 Nginx 反代和日志监控。
当前架构里每一块的"企业版替身"都想清楚了，这比盲目堆技术栈更重要。

## 简历项目描述（可直接抄）

**施工规范审查智能 Agent**（个人项目）｜Python / LangChain / LangGraph / Ollama / FAISS / Docker

- 构建多格式规范文档摄取管线：支持文字版/扫描版 PDF（RapidOCR）与 Word，pdfplumber 表格提取，
  针对真实 PDF 文字层缺陷设计编号清洗规则，实现条文级切分并附规范号/条文号/页码元数据；

## 已知局限与下一步（面试被问"不足"时用）

- 评测集规模小且自出题，计划扩充盲测集、引入排序指标和 rerank 二阶段精排；
- 条文号正则对非标准排版仍有少量误判，可加条文号序列连续性校验；
- 7B 模型工具调用偶发不稳定，生产应换更大模型 + 输出硬校验；
- 单 Agent 架构，计划升级为审查/报告/复核多 Agent 协作（LangGraph 子图）；
- 扫描版 OCR 未处理表格（表格识别需要专门模型，如 PaddleOCR 的表格结构识别）。
